# Panels are addressed by left-to-right position; with several open, a command must name one

A page can hold several panels (juicebox.js browsers side by side, CONTEXT.md: panel), and every command used to act on `hic.getCurrentBrowser()`. In the first Cowork trial (ticket 24) the model opened heart and colon side by side, then loaded CTCF, DNase and gene tracks meant for both: all four landed in the colon panel, the last one created and so the current one. The model had no way to say which panel it meant.

So every one-panel command takes `panel`: a 1-based position from the left, the primary form, because that is what the user sees and `list_panels` prints; or a map name, case-insensitive, as a convenience that is refused when two panels show the same map; or `"all"`, a plain loop over the panels that answers one line per panel and fails only when every panel fails. `load_map` also takes `"new"`. With one panel open `panel` may be omitted; with several, omitting it is an error that lists the panels, so the model asks or retries instead of hitting whichever panel happens to be current. With `"all"`, a track command must name its track: a track number is a position in one panel's list, so it would be a different track in each panel and is refused. There is no `select_panel`, and juicebox.js's own "targets" fan-out is not used; the remote resolves `panel` itself.

Rejected: juicebox.js's browser guid (stable, but the model would have to copy opaque ids around, and users never see them); map name only (two panels of the same map, or a panel with no map, cannot be named); a `select_panel` tool that sets a current panel (hidden state the model loses track of across turns, and the Cowork failure was exactly a wrong current panel); omitted meaning the current panel (the failure itself).

Consequences: positions shift when a panel closes, so `close_panel` answers with the remaining numbering. Sync events between pages still follow only the current panel, so peers that each hold several panels drift apart (ticket 29). `close_panel` calls `browser.registry.delete(browser)`, which is what juicebox.js's `deleteBrowser` does, because juicebox.js 4.7.0 does not export `deleteBrowser`; juicebox.js should export it (a ticket for the fork).
