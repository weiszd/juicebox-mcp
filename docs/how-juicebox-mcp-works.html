How Juicebox MCP works

Four parts work together so that Claude can operate a Juicebox contact map. This document says what each part does and what passes between them.

The four parts

PartWhat it doesWhat it does not do
ClaudeHolds the conversation. Decides which tool to call and with what values.Draw anything, or send commands to the page itself.
MCP serverOffers Claude 32 tools. Passes each tool call to the page as a command and returns the page’s reply.Serve the page, or handle any map data.
Juicebox web serverDelivers the files of the Juicebox page to a browser.Take any part once the page has loaded.
Juicebox pageDraws the contact map and carries out the commands. Fetches map data itself, directly from the public data hosts.Know anything about Claude.
The MCP server is a Cloudflare Worker. The Juicebox web server is a Cloudflare Pages site built from juicebox-web. They are deployed separately.

MCP, the Model Context Protocol, is a standard that lets Claude call functions offered by an outside server. Each function is called a tool. A connector is Claude’s name for an MCP server that a user has added to Claude.

The connector

The user adds the connector once, in Claude’s settings, by giving the address of the MCP server. In the development setup this is https://juicebot-mcp-dev.3dg.io/mcp.

The connector belongs to the user’s account, so one connector serves both Claude Desktop and Claude on the web. Claude’s requests to the MCP server come from Anthropic’s servers, not from the user’s computer. The MCP server must therefore have a public address.

Once the connector is switched on in a conversation, Claude can see the list of tools: load_map, goto_locus, set_color_scale, load_track and so on.

Where the page appears

The Juicebox page is an ordinary web page. It can be shown in one of two places.

Claude does not allow a connector to place another web site inside the conversation itself. That is why the page is shown in the panel or in a separate window, and not in the card.

A. The panel. Claude Desktop has a built-in browser panel beside the conversation. Claude opens the page there itself. The conversation and the map sit side by side in one window.

B. A separate window. Claude on the web has no panel. Claude shows a card with an Open Juicebox button, and the button opens the page in a browser window. A Claude Desktop user can choose this too: the card offers a link for it.

From first request to first map

The userWhat happens
1Asks Claude to open Juicebox.Claude calls the tool get_juicebox_url. The MCP server replies with a join link: the address of the Juicebox page with a room id attached, such as https://juicebot-dev.3dg.io/?room=7KQ2M9XA4T. Claude shows a card.
2In Claude Desktop, nothing; may be asked to allow the site. On the web, presses Open Juicebox.The join link is opened, in the panel by Claude or in a browser window by the button.
3Sees the Juicebox page appear.The browser fetches the page’s files from the Juicebox web server.
4Nothing.The page reads the room id from its own address, opens a connection to the MCP server and joins that room. The connection stays open.
5Asks for a map, a region, a colour, a track.Claude calls a tool. The MCP server sends a command down the open connection. The page carries it out and replies. The MCP server returns the result to Claude.
The behaviour in steps 1 and 2 is the current prototype, on the branch proto/first-launch.

The room id is what ties a conversation to a page. The MCP server creates one when a conversation starts and puts it in the join link. The page hands it back when it connects. From then on the MCP server knows which page a tool call from that conversation is meant for.

Each conversation has its own room. A page opened for one conversation does not respond to another.

One tool call

Step 5 is the working cycle. The MCP server does not draw and does not load data. It translates the tool call into a command, sends it, and waits up to ten seconds for the page to reply.

What happensWhat Claude is told
The page replies that it workedDone, with a short description
The page replies with an errorThe page’s error message
No reply within 10 seconds“Sent, unconfirmed”
No page has joined the room“No page is connected to this room”, with advice to open the join link

Claude turns what it is told into its answer to the user. The last row is the one a user meets most often: the page was never opened, or was closed.

A few tools do not involve the page. The search tools look up maps in the ENCODE and 4DN catalogues and answer from the MCP server alone.

Inside the page

The page contains two things. The viewer is juicebox.js, which draws the map. The remote is a small library that holds the connection to the MCP server. When a command arrives, the remote makes the matching call on the viewer and sends back the reply.

The viewer has no knowledge of Claude or of the MCP server. All of that is confined to the remote.

How the parts find each other

Four settings connect the parts. Each is an address held by one part that points at another.

SettingHeld byPoints atUsed for
Connector addressClaudeMCP server, /mcpTool calls
BROWSER_URLMCP serverJuicebox web serverBuilding the join link
VITE_WS_URLJuicebox pageMCP server, /wsThe page’s connection
ALLOWED_ORIGINSMCP serverJuicebox web serverRefusing connections from pages served anywhere else

VITE_WS_URL is fixed when the page is built. A page built for one MCP server cannot connect to another. An MCP server and a Juicebox web server are therefore deployed as a matched pair.
